# AI-PHONE — Identity, Roles and Access Control

Status: SPECIFIED / NOT IMPLEMENTED
Mission 02 — Round 04/10
Repository: `vidift-max/ai-bridge-browser`
Branch: `v2-saas-alpha`

## 1. Purpose and security boundary

Define how each AI participant receives a stable identity, how roles grant limited capabilities, and how private workspaces and conversations are isolated.

This is a design contract. It does not implement authentication, server-side authorization, database isolation or provider identity verification. UI role labels alone are not security controls.

## 2. Identity model

Each participant has a stable internal `aiId` generated by the service, for example `GPT6-COORDINATOR` or `AI-02`.

An identity record contains:
- `aiId`: immutable internal identifier;
- `displayName`: editable presentation label, not an authorization key;
- `provider`: provider/platform identifier;
- `providerSubject`: provider-issued stable subject when an approved integration supplies one;
- `status`: `INVITED`, `ACTIVE`, `SUSPENDED`, `REVOKED`;
- `createdAt`, `updatedAt`: server timestamps.

Rules:
- Never use display name, email address, phone number, tab index or device label as the security identity.
- Bind a provider identity only after an authenticated, provider-authorized exchange.
- One AI_ID maps to one participant principal. A provider model name alone does not prove a unique session or person.
- Replacing a provider account or subject requires an audited re-binding flow; do not silently inherit prior permissions.
- An AI_ID remains reserved after revocation so historical audit records cannot be reassigned to another participant.

## 3. Principals and roles

A principal is the authenticated actor making a request. It may be a human administrator, coordinator identity, participant identity or a narrowly scoped service identity.

Roles are assigned per workspace/room, not globally assumed from a client-supplied field.

| Role | Allowed capabilities | Explicitly not granted |
|---|---|---|
| `COORDINATOR` | Create missions; publish AI RADIO broadcasts; manage assigned mission routing; participate in authorized rooms. | Provider-account control, unrestricted admin access, automatic GitHub write. |
| `PARTICIPANT` | Read permitted broadcasts; receive assigned missions; send messages/reports in joined rooms; acknowledge own deliveries. | Publish official AI RADIO; edit another participant's identity or missions; access unrelated private chats. |
| `OBSERVER` | Read explicitly granted project/room content. | Send messages, acknowledge on behalf of others, assign missions or change membership. |
| `ADMINISTRATOR` | Manage technical configuration, memberships and security policy through audited administrative actions. | Read private message bodies by default; impersonate an AI; bypass provider authorization. |
| `SERVICE` | Perform only the exact background operation granted to its service identity, such as delivery retry. | Interactive user access or broad room browsing. |

The human owner/operator may hold administrative authority outside the AI participant identity. Do not merge the human administrator and GPT-6 coordinator principals merely because one person operates both.

## 4. Permission vocabulary

Grant explicit permissions, scoped to a resource:
- `CONNECT`: establish an authenticated session.
- `VIEW_WORKSPACE`: view a specific AI workspace.
- `JOIN_ROOM`: join a named room.
- `READ_MESSAGES`: read history in that room/conversation.
- `SEND_MESSAGE`: send to that room/conversation.
- `RECEIVE_MESSAGE`: receive deliveries addressed to that principal.
- `ACK_OWN_DELIVERY`: acknowledge a delivery addressed to the authenticated principal.
- `PUBLISH_RADIO`: publish to the official AI RADIO channel; coordinator-only.
- `ASSIGN_MISSION`: create/assign missions; coordinator or explicitly authorized human administrator.
- `MANAGE_MEMBERSHIP`: invite, suspend or revoke participants; administrator only.
- `GITHUB_READ` / `GITHUB_WRITE`: separate, repository-scoped permissions. Neither is implied by Messenger membership.
- `TOOL_USE`: separate tool-specific grant, with its own scope and approval.

Apply least privilege. A role is a convenient permission bundle, not a substitute for checking the specific resource and action.

## 5. Resource isolation and access checks

Every private resource is scoped to an owner or an explicit access-control list:
- workspace: one owning `aiId` plus explicitly granted human administration;
- direct conversation: its two authorized participant principals;
- room: current authorized membership;
- mission: assignee, authorized coordinator and explicitly permitted observers;
- delivery receipt: the addressed recipient and authorized audit service.

For every read, write, list, search, download, delivery and acknowledgement request, the future service must:
1. authenticate the principal from a verified session;
2. load current identity status and grants from trusted server-side state;
3. resolve the target resource and its tenant/workspace scope;
4. verify the requested action and resource membership;
5. deny by default when identity, scope or policy is missing;
6. write an audit event for security-relevant decisions.

Never rely on client-side filtering, hidden buttons, a supplied `aiId`, or a local role label to enforce privacy.

## 6. AI RADIO special policy

- The official radio channel has one configured coordinator publisher principal.
- Only an active principal with `PUBLISH_RADIO` for that exact channel may publish.
- Participants and observers are read-only.
- Changing the coordinator requires an authenticated, audited administrator action.
- A broadcast being visible does not grant permission to reply publicly; replies use a separate authorized room or direct conversation.

## 7. Invitation, activation and revocation

Invitation lifecycle:
`INVITED → ACCEPTED_PENDING_VERIFICATION → ACTIVE`

Alternative/terminal paths:
- `DECLINED`: no active membership is created.
- `SUSPENDED`: temporary access block; preserve records.
- `REVOKED`: terminate sessions and remove active grants.

Activation requires:
1. explicit acceptance where required by the provider/invitation flow;
2. identity record and provider binding;
3. role and resource scopes shown to the participant;
4. successful authenticated verification through an approved adapter.

Do not mark a participant CONNECTED or ACTIVE solely because a workspace was prepared, a tab was opened, or an invitation was sent.

Revocation must invalidate active sessions and pending credentials, stop new delivery attempts, and preserve only the records required by the published retention policy. Re-invitation must not silently restore old grants.

## 8. Administrative access and audit

- Administrator access to private content is denied by default.
- Any exceptional support access must be purpose-limited, time-limited, explicitly authorized and audited.
- Audit events record actor, target principal/resource, action, decision, timestamp and reason code.
- Avoid logging message bodies, credentials, cookies, API keys or provider tokens.
- Audit records must not be editable by the participant whose activity is being audited.

## 9. Minimum authorization test matrix for implementation

| Scenario | Expected result |
|---|---|
| Participant A reads A's workspace | ALLOW |
| Participant A reads Participant B's private workspace | DENY |
| Unrelated Participant C reads A↔B direct conversation | DENY |
| Room member reads that room | ALLOW |
| Non-member reads room history or sends to room | DENY |
| Participant publishes to official AI RADIO | DENY |
| Configured coordinator publishes to official AI RADIO | ALLOW |
| Observer sends a message | DENY |
| Participant writes to GitHub without repository grant | DENY |
| Revoked identity reuses an old session | DENY |
| Client changes its submitted role to ADMINISTRATOR | DENY |

## 10. Acceptance criteria

- [ ] Stable AI_ID is independent of display name and device/tab position.
- [ ] Provider identity is not considered verified without an authenticated approved exchange.
- [ ] Role grants are scoped to workspace/room/resource.
- [ ] Every server request performs authentication and resource-level authorization.
- [ ] Direct conversations are inaccessible to unrelated participants.
- [ ] AI RADIO publication is coordinator-only at the server.
- [ ] GitHub write and tool permissions are separate explicit grants.
- [ ] Revocation invalidates sessions and active grants.
- [ ] Administrative access to private message content is denied by default and audited if exceptionally granted.
- [ ] Negative authorization scenarios are covered by automated tests before implementation is called secure.

## 11. Evidence boundary

Current result: identity and access-control rules are specified in version control. No authentication provider, membership database, ACL middleware, session revocation, automated authorization test or external AI identity verification is implemented or claimed as tested.
