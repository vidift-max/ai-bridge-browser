# Mission 90 — Staging and Invite Activation

## Objective

Bring the implemented invitation/admission flow to a controlled staging target so the real browser flow can be tested without touching production or physical AI-PHONE devices.

## Ten rounds

1. Audited M89 and confirmed the invitation backend, `/invite` page, room invite UI, join-request UI, and HTTP E2E coverage already exist on the M89 line.
2. Created a dedicated Mission 90 branch from M89; no merge, reset, force-push, or production deployment.
3. Added an isolated Render staging Blueprint with persistent SQLite storage mounted at `/var/data`.
4. Bound staging identities explicitly to `AI-01` and `AI-02`; invitation credentials remain secret environment variables.
5. Kept storage mode explicitly `persistent`; ephemeral storage is not an acceptable readiness state for this service.
6. Kept OpenAI credentials optional and external to the invitation test; no provider account is activated by the invite.
7. Added a dedicated CI workflow for invitation/admission regression plus staging-contract validation.
8. Added a local contract test that rejects unsafe staging configuration such as ephemeral storage or missing persistent DB paths.
9. Verified the existing HTTP E2E covers invite creation, public metadata lookup, guest redemption, pending request, admin approval, membership refresh, revocation, and invite-page security headers.
10. Staging deployment remains a separately authorized external action; this PR only prepares and validates the activation package.

## Staging activation contract

Required secrets:
- `MESSENGER_TOKEN_AI_A`
- `MESSENGER_TOKEN_AI_B`

Required identity mapping:
- `MESSENGER_AI_ID_A=AI-01`
- `MESSENGER_AI_ID_B=AI-02`

Required persistence:
- `MESSENGER_STORAGE_MODE=persistent`
- `MESSENGER_PERSISTENT_STORAGE_ROOT=/var/data`
- `MESSENGER_DB_PATH=/var/data/messenger.sqlite`

The invite secret is generated by the server and is shown only in the creation response/UI. It is placed in the URL fragment so ordinary HTTP requests do not carry it as a query parameter.

## Real browser test sequence

1. Deploy the staging Blueprint only after explicit approval.
2. Open the staging `/rooms` page as the administrator.
3. Create a room-scoped invite and copy the generated link.
4. Open the link in a second browser/private window.
5. Submit the guest request.
6. Return to the admin browser and approve the pending request.
7. Confirm the guest sees the room and can participate through the authenticated room flow.
8. Exchange one text message and verify acknowledgement.
9. Revoke the invitation and verify that a new redemption is rejected.
10. Record the staging URL, deploy ID, commit SHA, test timestamps, and PASS/NO-GO result.

## Safety boundary

This mission does not merge PRs, does not provision external AI providers, does not activate a physical phone, and does not send production messages.
