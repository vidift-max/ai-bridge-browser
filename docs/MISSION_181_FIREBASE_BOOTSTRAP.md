# Mission 181 — Firebase bootstrap and controlled deployment

## Scope

This mission prepares the existing AI-Messenger Firebase project for a controlled deployment from GitHub. It is limited to AI-01 and AI-02. It does not create identity records, install an app, merge a pull request, or perform a deployment automatically.

## Project facts supplied by the operator

- Firebase project ID: `ai-messenger-b97df`
- Realtime Database URL: `https://ai-messenger-b97df-default-rtdb.firebaseio.com`
- Hosting origin: `https://ai-messenger-b97df.web.app`
- Hosting default site is provisioned, but the operator's Hosting page previously showed “Aguardando sua primeira versão”.
- Anonymous Authentication was enabled by the operator.
- Realtime Database was created in `us-central1`.
- The operator reported publishing the repository's database rules. This is operator-reported, not independently verified from the Firebase API.

## Repository configuration

- Firebase CLI config: `firebase/firebase.json`
- Realtime Database rules: `firebase/database.rules.json`
- Hosting content: `firebase/public/`
- Invite route: `/i/{conversationId}/{token}`
- Project alias: `firebase/.firebaserc`
- Static preflight: `node scripts/validate-firebase-project.mjs`

The Hosting public directory is `public`, relative to the directory containing `firebase/firebase.json`. Do not change it to `firebase/public`: the Firebase CLI resolves paths relative to the selected config directory. The database rules path `database.rules.json` is also relative to that directory.

## GitHub deployment workflow

Workflow: `.github/workflows/firebase-ai-messenger-deploy.yml`

It is manual-only (`workflow_dispatch`). It requires the exact input `DEPLOY_AI_MESSENGER`, validates the checked-in Firebase files before authentication, uses Google Workload Identity Federation (no downloaded service-account key), and deploys only Hosting plus Realtime Database rules to the fixed project ID.

The workflow will fail closed if either GitHub repository variable is missing:

- `FIREBASE_WORKLOAD_IDENTITY_PROVIDER`: full provider resource name, e.g. `projects/PROJECT_NUMBER/locations/global/workloadIdentityPools/POOL_ID/providers/PROVIDER_ID`.
- `FIREBASE_DEPLOY_SERVICE_ACCOUNT`: deploy service-account email.

No GitHub secret or Google credential was read or changed by this mission.

## One-time Google Cloud IAM setup required before manual deployment

An administrator of the Google Cloud project must:

1. Open Google Cloud Console for project `ai-messenger-b97df`.
2. Create a dedicated service account, for example `github-firebase-deployer`.
3. Grant that service account only the deployment roles required for this repository:
   - Firebase Hosting Admin (`roles/firebasehosting.admin`);
   - Firebase Realtime Database Admin (`roles/firebasedatabase.admin`);
   - Service Usage Consumer (`roles/serviceusage.serviceUsageConsumer`) if required by the project APIs.
4. Create a Workload Identity Pool and GitHub OIDC provider.
5. Map `google.subject=assertion.sub` and `attribute.repository=assertion.repository`.
6. Restrict the provider with the attribute condition `assertion.repository == 'vidift-max/ai-bridge-browser'`.
7. Grant the repository principal set `roles/iam.workloadIdentityUser` on the dedicated service account. Use the pool's exact project number and pool ID in the principal set.
8. In GitHub repository Settings → Secrets and variables → Actions → Variables, create the two variables listed above. These are identifiers, not private keys.

Do not create or upload a long-lived service-account JSON key. Do not put API keys, ID tokens, refresh tokens, or service-account credentials in Git.

## Operator action still required

The operator must complete the one-time IAM/WIF setup and populate the two GitHub repository variables. Then, after reviewing the pull request and explicitly deciding to publish, an authorized operator can run the workflow from GitHub Actions and enter `DEPLOY_AI_MESSENGER`.

The workflow is not run by pull requests, does not deploy previews, and does not run automatically on push.

## Post-deployment verification

After an explicitly authorized workflow run reports success:

1. Open `https://ai-messenger-b97df.web.app/i/example/AAAAAAAAAAAAAAAAAAAA` only as a route smoke test; it should show the invite page's invalid-link response for malformed route segments if the token shape is invalid.
2. Confirm `https://ai-messenger-b97df.web.app/` responds. A 404 at the root is not by itself proof that the invite route failed; the supported content is under `/i/**`.
3. Test a real, unexpired invitation generated by AI-01 on AI-02.
4. Do not claim live messaging until authenticated messages and acknowledgements are observed in both directions on the two devices.

## Explicit non-claims

This repository change does not prove that the Firebase project is reachable, that rules were actually published, that Hosting has been deployed, that IAM/WIF exists, that either device is configured, or that AI-01 and AI-02 have exchanged a message. No deployment, merge, release, installation, or identity bootstrap was performed.
